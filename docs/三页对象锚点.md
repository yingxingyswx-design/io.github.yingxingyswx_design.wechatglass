# 三页对象锚点（通讯录 / 发现 / 我）

> 2026-11-25 真机探针结果（`PageProbe`，tag `WeChatGlassProbe`）。原则：**找对象，不找名字**。
> 类名/资源 id 只作为“进入对象图的入口”，拿到对象后一律用框架 API 操作该对象。
> 原始日志：`debug/probe_all.txt`、`debug/probe_contacts3.txt`、`debug/probe_pref.txt`。

## 1. 入口：从 pager 对象拿到页面对象

已持有对象：`HomeGlassHook.pagerView`（`WxViewPager`）。

```
pagerView (WxViewPager)
├─ getAdapter()                         ← PagerAdapter 对象（hook instantiateItem 拿页面对象）
└─ getChildAt(0..3)  → 4 个 com.tencent.mm.ui.FrostedContentView（id 0x7f0a49e8）
   顺序固定：[0] 微信 / [1] 通讯录 / [2] 发现 / [3] 我
```

每个 `FrostedContentView` 内部结构（对象链）：

```
FrostedContentView
└─ MMWeUIBounceView (id 0x7f0a49ff)
   ├─ NestedScrollView
   └─ FrameLayout                      ← 真正的页面内容宿主，我们的页面挂这里
      └─ MainUIView / WxRecyclerView / RelativeLayout(...)
```

实测要点：

- **页面对象会重建**：切 tab 后 `FrostedContentView` 的 identityHashCode 变（例：`31888166` → 新对象），
  所以我们的覆盖页必须能“按页面对象”重挂，不能只挂一次。
- **adapter 异步就绪**：页面刚创建时 `getAdapter()` 返回 `null`，约 1–2s 后才有；
  页面对象 dump 要在切页后延迟重试（探针已用 900ms / 2200ms 两次）。
- `instantiateItem(ViewGroup, int)` 的返回对象即页面对象，`destroyItem` 可用来清理我们的覆盖页。

## 3. 通讯录（tab 1）

| 项 | 对象 / 值 |
|---|---|
| 列表对象 | `com.tencent.mm.view.recyclerview.WxRecyclerView`（id `0x7f0a0262`） |
| 字母索引对象 | `AlphabetScrollBar`（id `0x7f0a0272`） |
| adapter | `su3.y1`，`count=36` |
| adapter 数据 | 字段 `data` List size=34，**34 项全是同一个 `bq5.g` 占位对象** |
| 点击监听 | `mOnItemClickListener = null`（RecyclerView，没有列表级 listener） |

结论：
- 这是**分节（section）型 adapter**：`bq5.g` 是占位/多类型 item，单条联系人数据不从这里暴露；
  硬拆它需要再往下挖 `v`/`w` 两个 Map 和 `i`/`m` 两个列表，收益低、易碎。
- **因此通讯录采用：数据来自 `ConversationIndex`（只读 SQL）+ 点击走原生资料页**（见下）。

### 3.1 原生列表的 UI 组成（真机实测，截图 `debug/contacts_now.png`）

| 位置 | 对象 | 内容 |
|---|---|---|
| item 0 | `LinearLayout`（h=874，可点） | 入口块，内含 新しい友人 / チャットのみの友達 / グループチャット / タグ / サービスアカウント / WeCom連絡先 |
| 其后 | `LinearLayout`（h=210） | 分组标题：スター付き、A、C …（**不是** sticky header，就是普通 item） |
| 联系人行 | `LinearLayout`（h=133，可点） | children = `RelativeLayout`（头像）+ `LinearLayout`（名字）；`row.tag = null`，**行对象里没有 username** |

右侧字母条是独立对象 `AlphabetScrollBar`（id `0x7f0a0272`）。

### 3.2 rcontact 的拼音列（可直接用，不用自己算拼音）

`pragma table_info(rcontact)` 实测列（节选）：
`username, alias, conRemark, nickname, pyInitial, quanPin, showHead, type, uiType,
conRemarkPYFull, conRemarkPYShort, verifyFlag, deleteFlag, ...`

实测值：

```
user=wxid_rqu7...  py=AS15MHYWBZSC  quan=ansang15mihaoyouweibuzhuaishanchu  nick=安桑（15米好友位 不转删除）
user=wxid_c7l9...  py=CSD          quan=chaoshidai                      remark=パパ  nick=超时代
user=wxid_5c82...  py=CX           quan=chouxiang                      nick=抽象
user=wxid_ggj0...  py=1256?        quan=1256?                          remark=箱子  nick=12:56🥔
```

三个关键事实：

1. `pyInitial` 是**按昵称算的拼音首字母**，不是按备注算的 —— 所以备注叫「パパ」的人因为昵称「超时代」而排在 **C** 段。
   原生列表就是这么排的，我们照抄即可（分区用 `pyInitial[0]`，显示用 `conRemark` 优先）。
2. 数字/英文名字的首字母可能是数字（`1`）或大写字母；带非字母字符时微信会在后面加 `?`（`1256?`、`CQ?`）。
   分区规则：首字符是 A–Z 就用它，否则归 `#`。
3. **好友查询会把「自己」查出来**（`wxid_vc1iiekkyodr22` / 昵称 22:39），必须排除。

### 3.3 自己的 username（排除自己用）

`select * from userinfo` 是 key/value 表（`id, type, value`），实测：

```
id=2 type=3 value=wxid_vc1iiekkyodr22     ← 自己的 username
```

→ `select value from userinfo where id=2 and type=3` 即可拿到自己，通讯录页把它过滤掉。

### 3.4 打开联系人资料页（实测通过）

原生点击后 `dumpsys activity` 的 `topResumedActivity`：

```
com.tencent.mm/.plugin.profile.ui.ContactInfoUI
```

注意包路径是 **`plugin.profile.ui`**，不是老版本的 `ui.contact`（后者在 8.0.79 已不存在，
`ActivityNotFoundException` 实测过）。用 `Contact_User` 传 username 即可打开，已实测进入「徐倫」资料页
（截图 `debug/contact_profile.png`）。

## 4. 发现（tab 2）

| 项 | 对象 / 值 |
|---|---|
| 列表对象 | `com.tencent.mm.ui.widget.listview.PullDownListView`（id `0x102000a`） |
| adapter | `com.tencent.mm.ui.base.preference.g0` |
| count | 9 |
| 点击 | `PullDownListView` 自己就是 `mOnItemClickListener`，用 `list.performItemClick(view, pos, id)` 原样转发 |

**重要：`getTitle()` / `getSummary()` / `getIcon()` 全部返回 null**（微信重写过，不填这些字段）。
标题必须读 Preference 对象的字段 `h`，图标读字段 `i`（资源 id），行布局读字段 `F`。

9 个对象的实际构成（日文 locale 账号）：

| idx | 类 | h（标题） | 说明 |
|---|---|---|---|
| 0 | `FriendSnsPreference` | モーメンツ | 朋友圈 |
| 1 | `PreferenceSmallCategory` | null | 分组空隙（不是可点行） |
| 2 | `ScanIconViewTipPreference` | スキャン | 扫一扫 |
| 3 | `PreferenceSmallCategory` | null | 空隙 |
| 4 | `NormalIconPreference` | 近くにいる人 | 附近 |
| 5 | `PreferenceSmallCategory` | null | 空隙 |
| 6 | `CustomSizeIconNewTipPreference` | ミニプログラム | 小程序 |
| 7 | `PreferenceSmallCategory` | null | 空隙 |
| 8 | `Preference` | null | 尾部占位/更多 |

结论：发现页可以**完全对象化**——遍历 `adapter.getItem(i)` 拿对象，读 `h`/`i`/`F`，
**跳过 `PreferenceSmallCategory`**（用它的位置决定分组间距），点击用 `performItemClick`。
不需要硬编码条目、不需要文本匹配、不需要猜 Intent。

## 6. 顶栏（结论：这里仍要按名字入口）

- `activity.getSupportActionBar()` 能拿到 ActionBar 对象（`mv5.q0`），但：
  - `getCustomView()` = **null**（微信用的是 Toolbar，不是 custom view）；
  - 该对象及其父类**没有任何 View 类型字段**，拿不到 `ActionBarContainer` 对象。
- 因此顶栏容器仍按类名入口取（现有 `findByClass(decor, "androidx.appcompat.widget.ActionBarContainer")`），
  这是“名字只用于入口”的例外，需在实现时保留并加注释。

## 7. 点击实测（已真机验证）

探针对发现页第 0 行（`FriendSnsPreference`）主动调用：

```
lv.performItemClick(row, 0, adapter.getItemId(0))
→ handled=true
→ 朋友圈页面被打开（截图 debug/clicktest.png）
→ 返回键回到发现页（截图 debug/after_back.png）
```

结论：**对象转发点击这条路成立**，不需要任何 Intent 类名。发现/我 两页的行点击照此实现。

注意：该账号发现页只有 4 个可点行（モーメンツ / スキャン / 近くにいる人 / ミニプログラム），
其余 5 项是 4 个 `PreferenceSmallCategory` 空隙 + 1 个尾部 `Preference` 占位。
分组必须按实际对象判断，不能按固定索引写死。

另：发现页当前顶部有一条约 280px 的空白（原生 ActionBar 被隐藏后没有补），
说明三页的 M3 大标题栏确实是必须补的。

## 9. 布局决定（2026-11-25，用户确认）

- **发现页**：M3E 2 列卡片网格（规范 §5.3）。
- **我页**：资料卡通栏 + 其余入口 2 列卡片网格。
- **通讯录页**：**不用**两列，保持单列列表 + A–Z 分区（几百行必须单列，两列会毁掉字母索引）。
- 三页统一：16dp 页边距、16dp 卡片间距、28dp 卡片圆角、卡片 `surfaceContainerLow`、标题 `titleMedium` 16sp。
